# 需求：参考图任务的会话复用策略（2026-09-20）

## 现状

带 `--input` 的任务在 `extension/content-core.js` 的 `startCleanConversation()` 中**一律先新建对话**，
然后才附加参考图并提交。该策略来自上一轮结论：干净会话可排除"历史上下文压过新参考图"，
并让提交后的附件证据可归属到本次任务。

代价：每个参考图任务都会在用户的 ChatGPT 侧边栏新增一个对话；当参考图**固定不变**
（例如固定的角色参考图）时，这个代价没有换来对应的收益。

## 用户诉求

当参考图与上一次相同时（固定角色/固定风格场景），**复用同一个对话**即可，不必每次新建。

## 需要方案裁定的问题

1. 复用会话是否会破坏提交后校验？
   现有校验要求"新提交的用户轮次中恰好有 N 个附件单元"，且只作用于最新用户轮次——
   初步判断与"哪个对话"无关，但仍需确认在复用会话时该判据依然成立。
2. 上下文漂移风险如何界定？同一张参考图时风险较低；但同一参考图 + 差异很大的提示词时，
   历史生成结果可能影响风格。是否需要按提示词差异度决定？
3. 是否需要复用上限（例如最多连续 N 次、或跨天后强制新建），避免上下文无限增长？
4. 参考图"相同"如何判定？建议：参考图字节哈希 + 顺序 + MIME 的指纹，而非文件名。
5. 策略如何暴露？候选：CLI 参数（如 `--conversation reuse|new|auto`）、环境变量、
   或默认 `auto`（指纹相同则复用，否则新建）。是否需要显式强制新建的开关？
6. 桥/扩展侧需要在何处保存"上次参考图指纹 + 会话 URL"？专用标签页的 `chrome.storage.local`
   还是桥的作业记录？需考虑多任务串行与标签页被关闭的情况。

## 约束（不得违反）

- 复用会话不得削弱提交后校验：轮次里没有恰好 N 个附件单元时仍必须失败
- 不得因复用而跳过"上传就绪"的有界等待
- 参考图任务仍不得降级为无参考图生成
- 变更需可测试（现有 59 个测试为基线），并需真机验证

## 实施后的实测结果（2026-09-21）

### 已实现（扩展 0.3.2）

- 复用判定与状态所有权在 **service worker**：读资格记录 → 比对有序指纹与会话 ID →
  随 job 下发 `conversationDecision: reuse|new`；成功后记录资格，失败清除
- 内容脚本**不做任何存储 IO**，只执行 `conversationDecision`
- `--conversation auto|new|reuse`（env `IMAGE_BRIDGE_CONVERSATION` 为回退）
- 存储访问带 1.5 秒超时；已按用户要求**移除** 5 次/24 小时强制上限
- 测试：68 通过（15 文件），typecheck/build 全绿

### 真机结果

| 步骤 | 决策 | 期望 | 实际 |
| --- | --- | --- | --- |
| 1. 参考图 A | 新建 | 新建会话 | ✅ ok，29 秒，新建 `6ab01a95` |
| 2. 同一张 A | **复用** | 复用 `6ab01a95` | ❌ 301 秒 TIMEOUT，且**新建了 `6ab01b2f`** |
| 3.（上一轮）参考图 B | 新建 | 新建会话 | ✅ ok |

Chrome 历史时间戳：`6ab01a95` 首访 02:07:19（第 1 步，CLI 已回报）；`6ab01b2f` 首访 02:08:39，
落在第 2 步执行窗口内 → **第 2 步走了"新建"分支**。

### 尚未确定的部分

1. 判定为何是 `new`：资格记录未写入 / 未读到 / 记录中的会话 ID 与任务领取时的 tab URL 不一致？
2. 判定为 `reuse` 时字段是否真的送达内容脚本并生效？
3. 第 2 步的 301 秒 TIMEOUT：走新建路径时也偶发（其它轮次新建也有过一次 300 秒无出图），
   与复用是否生效无关；疑似与限流有关，未证实。

### 关键教训（方法层面）

这一功能连续多轮出现"证据不足时靠推断下结论、随后被实测推翻"：
- 曾把 `TIMEOUT` 误读为"已通过提交后校验"
- 曾把限流造成的失败归因为代码缺陷，随后又反向更正
- 本轮又把"复用可能已生效"当成结论，被会话时间戳推翻

根因是**执行过程没有记录关键决策**，只能靠外部证据反推。

### 提议（待裁定）

- 增加 **dry-run**：仅执行"读资格记录 → 比对指纹与会话 ID → 输出判定"，
  不附加文件、不提交、不创建会话，可在不消耗 ChatGPT 会话与不触发限流的前提下验证判定链路
- 增加**分级诊断**：错误/结果中带"卡在哪个阶段"（会话准备 / 上传就绪 / 提交后校验 /
  等待助手回复 / 等待出图），以及判定用的关键值（是否读到记录、两个会话 ID、最终判定）
- 在判定链路具备自证能力之前，暂停真机验证，避免继续产生无用会话与限流风险

## 真机验证通过（2026-09-21，扩展 0.3.4）

| 步骤 | 判定 | 记录计数 | 结果 |
| --- | --- | --- | --- |
| 1. 参考图 A | `new` / `reason: no_record` | 写入后 `successfulJobs: 1` | ok，35 秒，新建 `6ab09dad` |
| 2. 同一张 A | **`reuse` / `reason: record_matches`** | **`successfulJobs: 2`** | ok，36 秒，**同一会话 `6ab09dad`** |

第 2 次判定明细（直接观测，非推断）：
`hasRecord: true`、`recordFingerprintMatches: true`、`recordConversationMatches: true`、
`currentConversationId == recordConversationId == 6ab09dad`。

用户端确认：**该会话内有两条消息，各自都带参考图缩略图**。

关键：`/v1/status` 暴露的 `reuseRecord` 与 `lastConversationDecision` 让整条判定链可观测，
无需再靠 Chrome 历史时间戳或超时长度反推——这正是本次能一次定性的原因。

### 仍未验证
- 取不同参考图时应新建会话（指纹变化分支）在 0.3.4 上尚未复测
- `--conversation new` / `reuse` 的显式行为未做真机验证
- 分阶段诊断（卡在哪个阶段）与写入确认仍未实现

### 指纹变化分支验证（2026-09-21，0.3.4）

| 输入 | decision | reason | 会话 |
| --- | --- | --- | --- |
| 参考图 A（首次，无记录） | new | `no_record` | 新建 `6ab09dad` |
| 参考图 A（再次，记录匹配） | **reuse** | `record_matches` | **仍是 `6ab09dad`** |
| 参考图 B（指纹变化） | new | `fingerprint_changed` | 新建 `6ab0a1b8` |

第三条的 details 很关键：`hasRecord: true`、`recordConversationMatches: true`、
**`recordFingerprintMatches: false`** —— 记录存在、标签页也在记录的那个会话上，
唯一变化的是参考图指纹，判定因此正确地选择了新建。

三条判定理由各自独立命中，说明判定链的区分能力正确（不是"碰巧新建/碰巧复用"）。
