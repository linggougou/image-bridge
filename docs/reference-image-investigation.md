# 参考图上传问题调查记录（2026-09-18）

## 结论状态

**已定方案，代码已实现，待真机复验。**

采纳的信任模型（C2C 任务 c2c_db06）：

1. 上传成功与否**不看** file input 的 files 数量，也不看 composer 预览数量——
   两者只证明 DOM 赋值生效，不足以证明 ChatGPT 接受了附件。
2. 唯一可信判据是**新提交的用户轮次本身**显示出预期数量的附件单元，
   且数量必须**等于**本次任务提交的参考图数量。
3. 附件单元按"单位"计数：一个附件容器与其内部图片算一个，
   绝不重复计数，避免"N 张里只活下来 1 张"被判为通过。
4. 参考图任务必须在**干净会话**中执行（本轮对话没有历史轮次），
   否则历史上下文会压过新的参考图，且附件证据无法归属到本次任务。
5. 任何一项证据缺失或含糊一律**失败关闭**，不做"降级为无参考图生成"。

引入的错误码：`REFERENCE_IMAGE_NOT_SUBMITTED`（提交后校验失败，终态，不产出图片）。

## 历史：修复前的代码事实（已过时，见顶部结论）

`extension/content-core.js` 的 `attachReferenceImages` 判定"上传成功"的条件是：

1. `fileInput.files.length >= 已有文件数 + 本次输入数`
   —— 这是同义反复：赋值成功它必然成立，不能证明 ChatGPT 接受了文件。
2. `composerAttachmentCount(composer) >= 基线 + 本次输入数`
   —— 取根逻辑为 `composer.closest("form") || composer.parentElement || document`。
   若退化为宽容器或 `document`，会话历史里已有的图片可能被计入。

`extension/chatgpt-main-world.js` 是实际执行附加的路径（MAIN world），
判定条件与上面一致，同样只回传 `ok` 与 `count`。

因此当前的 `ok: true` **不能**作为"图片已上传到消息里"的证据。

## 历史：当时的待定问题（已由 c2c_db06 的 PLAN 定案，见顶部结论）

1. 如何取得"消息里真的带了附件"的可信判据？
   - 提交后检查新增的 user turn 是否含附件元素？
   - 还是必须依赖 ChatGPT 的自述（脆弱）？
2. 是否需要"每个任务一个干净会话"？
   - 实验 D 表明同会话上下文会压过新参考图，隔离能同时消除 A/B 两种歧义。
   - 但主世界脚本无法自行开新对话，需要考虑导航时机与 job 丢失风险。
3. 失败语义：如果无法确认附件已提交，应该直接失败（`REFERENCE_IMAGE_UPLOAD_FAILED`）
   还是降级为"无参考图生成"？当前实现是后者（静默），这是本次问题的直接原因之一。

因此：

1. **参考图上传仍未真正生效**，早期"上传成功"的结论继续不成立。
2. 提交后校验的第一版实现存在假阳性：`countTurnAttachments` 把

3. 上传机制本身已改为**合成拖放优先**（React composer 的实际上传入口），
   file input 赋值降级为回退路径。此改动尚未真机验证。

结论：判据问题已修，**上传机制是否修好必须再跑一次真机验收**。

## 2026-09-19 第二次真机 + 根因修正

第二次真机（22:47 本地）结果与用户端观察：

- 未创建新会话（Chrome 历史只出现旧会话 `6aae9af2`）→ 隔离未触发
- 用户确认：**消息里没有参考图缩略图**，且页面上"好像没有新消息"（仍是 22:30 那条回复）
- 任务以 `TIMEOUT` 结束，未产出图片

### 结论修正（重要）

先前把 `TIMEOUT` 解读为"已越过提交后校验、只是没出图"，**这是错的**。
真实原因是超时预算被上传等待吃掉：

- `attachReferenceImages` 等待 composer 出现附件预览，用的超时是 `job.timeoutMs`（300 秒）
- CLI 侧截止时间同样是 300 秒

因此上传永远不成功时，扩展还没走到 `REFERENCE_IMAGE_UPLOAD_FAILED`，CLI 就先到点报 `TIMEOUT`。
`TIMEOUT` 在这种场景下**不代表任何阶段性成功**。

### 当前判定

- 参考图上传**从未真正生效**：drop 与 file input 两条路都未让 ChatGPT 接收文件
- 提交后校验的假阳性已修复（只认真正的附件图片），但**缺少实证手段判断上传断在哪**
- 隔离判断存在缺陷：任务开始时页面若未渲染完，会把历史会话误判成干净会话

### 下一步方向

1. 上传等待改为有界（20-30 秒），让失败明确表现为 `REFERENCE_IMAGE_UPLOAD_FAILED`
2. 判断"干净会话"前先等页面渲染稳定
3. 增加上传诊断：把实际找到的 file input（id/accept/是否在 composer 内）、drop 后 composer
   新增的节点、以及被判为附件图片的元素描述回传出来，用一次真机定位断点
